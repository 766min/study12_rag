## 2. 검색 전략 선택 기준 정립

<aside>
💡

**질문의 형태적 특징을 기반으로 가장 성공 확률이 높은 검색기를 짝지어주는 규칙을 만듭니다.**

</aside>

### 2.1 질의 유형별 최적 검색 전략 매핑

<aside>

질문에 쓰인 어휘와 찾고자 하는 정보의 성격에 따라 최적의 전략이 달라집니다.

| **질의 유형** | **대표적 특징** | **최적 검색 전략** | **선택 근거** |
| --- | --- | --- | --- |
| **고유명사·단순 키워드형** | 시스템 코드, 약어, 규정 조항 번호 포함 | **키워드 검색 (BM25)** | 단어 형태의 100% 일치가 핵심이므로 왜곡 없는 텍스트 매칭이 유리함 |
| **의미 탐색형** | 일상 구어체, 동의어, 상황 묘사 중심 | **벡터 검색 (Vector)** | 단어가 달라도 문맥적 의도를 파악하는 다차원 임베딩 유사도가 유리함 |
| **복합 조건형** | 여러 조건과 맥락이 얽힌 복합 질의 | **벡터 검색 (또는 Hybrid)** | 전체 문맥을 포괄적으로 해석해야 하므로 의미 기반 탐색이 우선됨 |
</aside>

### 2.2 동적 라우팅(Query Routing) 원리

<aside>

- **개념**: 사용자의 질문을 검색 엔진에 바로 보내지 않고, 분류기(Router)가 먼저 질문의 의도를 분석하는 기법입니다.
- **역할**: 고유명사는 키워드 검색기로 보내고, 서술형 문장은 벡터 검색기로 분기시켜 검색 누락을 방지합니다.
</aside>

## 3. 동적 검색 파이프라인 구현

<aside>
💡

LLM 모델을 라우터로 활용하여 질문에 적합한 검색기를 실시간으로 선택합니다.

</aside>

### 3.1 텍스트 데이터 준비 및 다중 검색기 생성

<aside>

사내 안내 문서를 바탕으로 키워드 검색기와 벡터 검색기를 각각 생성합니다.

```python
import os
from dotenv import load_dotenv
from langchain_core.documents import Document
from langchain_community.retrievers import BM25Retriever
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings

load_dotenv()

# 비교 분석 및 파이프라인에 사용할 사내 안내 문서를 정의합니다.
raw_documents = [
    Document(
        page_content="신규 입사자 OJT 교육 안내: 하반기 공채 신입사원 대상 OJT는 개더타운 메타버스 연수원에서 온라인 비대면으로 진행됩니다.",
        metadata={"category": "교육", "doc_id": 1}
    ),
    Document(
        page_content="사내 식당 운영 지침: 중식 운영 시간은 11시 30분부터 13시 30분까지이며 외부 방문객의 1회 식권 가격은 8,000원입니다.",
        metadata={"category": "복지", "doc_id": 2}
    ),
    Document(
        page_content="정보보안 규정: 직원이 퇴사하는 경우 모든 사내 전산망 및 인트라넷 계정 권한은 퇴사 당일 18시를 기점으로 영구 회수됩니다.",
        metadata={"category": "보안", "doc_id": 3}
    )
]

# 띄어쓰기 기준 공백 분리 토크나이저 함수를 정의합니다.
def simple_tokenizer(text: str) -> list[str]:
    # 텍스트를 공백 단위로 분할하여 리스트로 반환합니다.
    return text.split()

# 키워드 검색기 (BM25)를 생성하고 반환 개수를 1개로 설정합니다.
bm25_retriever = BM25Retriever.from_documents(
    documents=raw_documents,
    preprocess_func=simple_tokenizer
)
bm25_retriever.k = 1

# 벡터 검색기를 생성합니다. OpenAI 임베딩 모델을 사용합니다.
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vector_store = InMemoryVectorStore.from_documents(
    documents=raw_documents,
    embedding=embeddings
)
vector_retriever = vector_store.as_retriever(search_kwargs={"k": 1})
```

</aside>

### 3.2 LLM 모델 기반 질의 라우터 구현

<aside>

언어 모델을 호출하여 질문의 구조를 분석하고 적절한 검색기 식별자(`bm25` 또는 `vector`)를 판정합니다.

```python
from langchain.chat_models import init_chat_model
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser

model = init_chat_model(
    model="gpt-5-mini",
    model_provider="openai",
    temperature=0
)

# 질문의 특성을 분석하여 검색 전략을 판정하는 프롬프트를 정의합니다.
router_prompt = PromptTemplate.from_template(
    "당신은 검색 파이프라인의 질의 라우팅 전문가입니다.\n"
    "사용자의 [질문]을 검토하고 가장 적합한 검색기 이름을 정확히 하나만 출력하세요.\n\n"
    "- 질문에 특정 약어, 고유 명칭, 조항 번호 등 정확한 일치가 필요한 단어가 포함된 경우: bm25\n"
    "- 질문이 구어체이거나 의미/뉘앙스를 기반으로 탐색해야 하는 서술형인 경우: vector\n\n"
    "[질문]: {query}\n"
    "[선택 결과 (bm25 또는 vector만 출력)]:"
)

# 라우팅 결정을 내리는 체인을 생성합니다.
router_chain = router_prompt | model | StrOutputParser()
```

</aside>

### 3.3 조건부 분기 파이프라인 조립

<aside>

판정 결과에 따라 질문을 해당 검색기로 전달하고 문서를 가져오는 파이프라인을 완성합니다.

```python
# 라우팅 결과에 따라 검색기를 분기 실행하는 함수를 정의합니다.
def route_and_retrieve(query: str) -> dict:
    # LLM 모델을 호출하여 전략을 판정합니다.
    decision = router_chain.invoke({"query": query}).strip().lower()
    
    # 결정된 전략에 따라 적합한 검색기를 실행합니다.
    if "bm25" in decision:
        selected_strategy = "BM25 (키워드 검색)"
        retrieved_docs = bm25_retriever.invoke(query)
    else:
        selected_strategy = "Vector (의미 검색)"
        retrieved_docs = vector_retriever.invoke(query)
        
    # 전략명과 검색 결과를 묶어서 반환합니다.
    return {
        "strategy": selected_strategy,
        "content": retrieved_docs[0].page_content if retrieved_docs else "결과 없음"
    }
```

</aside>

## 4. 파이프라인 개선 효과 검증

<aside>
💡

단일 검색기 적용 시 발생했던 검색 실패 사례가 동적 라우팅을 통해 올바르게 개선되었는지 확인합니다.

</aside>

### 4.1 유형별 질의 대조 실행

<aside>

이전 강에서 사용했던 세 가지 테스트 케이스를 개선된 파이프라인에 전달하여 결과를 확인합니다. 

```python
# 테스트 케이스 목록을 준비합니다.
test_cases = [
    {"type": "고유명사형", "query": "개더타운 접속 일정"},
    {"type": "의미 탐색형", "query": "새로 들어온 신입 직원 교육은 어디서 하나요?"},
    {"type": "복합 조건형", "query": "퇴사할 때 사내 계정 정리는 몇 시에 진행돼?"}
]

print("=== [개선된 파이프라인 실행 및 검증] ===")

# 각 테스트 케이스를 순회하며 결과를 출력합니다.
for case in test_cases:
    query_type = case["type"]
    query_text = case["query"]
    
    # 동적 라우팅 검색을 실행합니다.
    result = route_and_retrieve(query_text)
    
    print(f"질문 유형: {query_type}")
    print(f"질문 내용: {query_text}")
    print(f"선택된 전략: {result['strategy']}")
    print(f"검색 결과 본문: {result['content']}")
    print("-" * 60)
```

### 4.2 개선 전후 비교 결과

<aside>

- **의미 탐색형 개선**: 단일 BM25 적용 시 어휘 불일치로 보안 규정 문서를 잘못 가져왔던 문제가, 파이프라인의 벡터 검색기 자동 선택을 통해 교육 안내 문서로 정상 교독되었습니다.
- **고유명사형 유지**: 특정 단어('개더타운')가 포함된 질의에 대해 키워드 검색기를 정확히 선택하여 불필요한 의미 왜곡 없이 원본 문서를 확보했습니다.

**Q2. 고유명사나 특정 사내 규정 코드 검색 시 LLM 라우터가 키워드 검색(BM25)을 선택하도록 설정하는 주된 이유는 무엇인가요?**

---

- [ ]  (1) 키워드 검색이 데이터베이스 연결을 전혀 요구하지 않기 때문에
- [ ]  (2) 임베딩 벡터 검색보다 키워드 검색이 항상 더 많은 문서를 반환하기 때문에
- [ ]  (3) 희귀한 문자열이나 일련번호의 형태를 있는 그대로 일치시키는 데 키워드 검색이 더 정확하기 때문에
- [ ]  (4) LLM 모델이 벡터 저장소와 호환되지 않기 때문에

- **답안 설명**
    
    **정답:** 3번
    
    임베딩 모델은 고유 식별자나 특수 코드를 일반 단어의 평균적인 의미로 흡수해 버릴 수 있으므로 형태를 보존하는 키워드 검색이 적합합니다. 
    
</aside>

### 5.2 개념 요약 키워드

- **질의 라우팅 (Query Routing)**: 입력된 질문의 어휘와 의도를 사전 분석하여 가장 적합한 검색 모듈로 작업을 전달하는 분기 기술
- **전략 선택 기준 (Strategy Criteria)**: 고유명사/규정 번호는 키워드 검색으로, 서술형 문장/동의어는 벡터 검색으로 연결하는 매핑 원칙
- **파이프라인 개선 (Pipeline Refinement)**: 단일 검색 방식의 한계로 발생하는 검색 실패를 다중 검색기 동적 연결을 통해 보완하는 작업

### 5.3 용어 사전

| 용어 | 영어 표현 | 설명 |
| --- | --- | --- |
| 질의 라우팅 | Query Routing | 질문의 유형에 따라 가장 적합한 검색기나 처리 파이프라인으로 연결하는 분기 기법입니다. |
| 어휘 불일치 | Vocabulary Mismatch | 질의와 문서의 의미는 같으나 글자 표기가 달라 키워드 매칭에 실패하는 현상입니다. |
| 온도 (무작위성) | Temperature | 언어 모델이 답변을 생성할 때 창의성과 무작위성의 정도를 조절하는 파라미터입니다. |
