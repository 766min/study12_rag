## 03. ETL과 청킹

| 03-1 | ETL: 추출(로더) → 변환(청킹·임베딩) → 적재(벡터 DB) | ✅ | 문서 로더 → 청크로 분할 → 임베딩 → 벡터 저장소 순서의 파이프라인 | [LangChain Docs: Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval) |

| 03-4 | `Recursive…` 기본 구분자 `["\n\n", "\n", " ", ""]` = 문단 → 줄 → 공백 → **마침표** (실습 `01_01` 주석) | ⚠️ | 기본 구분자 목록은 **맞다**. 하지만 마지막 `""`는 **글자 단위**로 자르라는 뜻이다(마침표가 아님). 공식 문서: 문단을 유지하려 하고, 크면 다음 단위로, 필요하면 단어 단위까지 내려간다 | `langchain_text_splitters/character.py` 107행, [LangChain Docs: Text splitters](https://docs.langchain.com/oss/python/integrations/splitters) |

| 03-6 | 청크 크기는 보통 200~1,000자 | ❓ | 공식 문서에 권장 범위가 없다. 참고로 LangChain 기본값은 4,000자, 겹침 200자 | `langchain_text_splitters/base.py` 64–65행 |
| 03-7 | 유사도가 낮으면 청크를 줄이고, 답이 엉뚱하면 늘린다 | ❓ | 이런 조정 규칙은 공식 문서에서 찾지 못했다. 공식 문서는 "대부분 `RecursiveCharacterTextSplitter` 기본값으로 시작하고, 필요할 때만 조정하라"고 한다 | [LangChain Docs: Text splitters](https://docs.langchain.com/oss/python/integrations/splitters) |
| 03-8 | PDF 속 표는 마크다운 표로 바꿔 넣는 게 낫다 | ❓ | 공식 근거를 찾지 못했다. 문서 구조(마크다운 제목, HTML 태그 등)를 따라 자르는 방식은 공식 문서에 있다 | [LangChain Docs: Text splitters](https://docs.langchain.com/oss/python/integrations/splitters) |
| 03-9 | `split_documents`는 잘린 청크마다 메타데이터를 복사한다 | ✅ | 청크마다 `copy.deepcopy(metadata)`로 복사한다. `add_start_index=True`면 원문 시작 위치도 넣어 준다 | `langchain_text_splitters/base.py` 130–142행 |
| 03-10 | `PyMuPDFLoader`는 페이지마다 Document 1개 | ✅ | 기본 `mode="page"`(페이지별). `mode="single"`이면 문서 전체가 Document 1개 | `langchain_community/document_loaders/pdf.py` 777행 |
| 03-11 | `CacheBackedEmbeddings`로 같은 글을 다시 임베딩하지 않는다. namespace로 구분 | ⚠️ | 문서 임베딩 캐시와 namespace(다른 모델과 키 충돌 방지)는 **맞다**. 단 `embed_query`는 **기본적으로 캐시하지 않는다**. 질문까지 캐시하려면 `query_embedding_cache=True`를 줘야 한다 | `langchain_classic/embeddings/cache.py` 241–255행, 293–309행 |

## 04. 벡터 저장소 (PGVector)

| 04-6 | IVFFlat: 벡터를 구역으로 나누고 가까운 구역만 찾는다 | ✅ | 벡터를 리스트로 나누고, 질문 벡터와 가까운 리스트 일부만 검색한다. HNSW보다 **빌드가 빠르고 메모리를 적게** 쓰지만 속도-재현율은 낮다. 데이터가 어느 정도 쌓인 **뒤에** 만들어야 한다 | [pgvector README](https://github.com/pgvector/pgvector/blob/master/README.md) |
| 04-7 | HNSW: 그래프로 연결해 이웃을 따라가며 찾는다 | ✅ | 다층(multilayer) 그래프를 만든다. IVFFlat보다 속도-재현율이 좋지만 빌드가 느리고 메모리를 더 쓴다. 학습 단계가 없어서 빈 테이블에도 만들 수 있다 | [pgvector README](https://github.com/pgvector/pgvector/blob/master/README.md) |
| 04-8 | `ids`를 주면 같은 id는 덮어쓴다 | ✅ | `on_conflict_do_update`(있으면 갱신)로 넣는다 | `langchain_postgres/vectorstores.py` 791·850행 |
| 04-9 | `ids` 없이 다시 실행하면 중복으로 쌓인다 | ✅ | ids가 없으면 매번 새 `uuid4()`를 만든다 → 같은 내용도 새 행이 된다 | `langchain_postgres/vectorstores.py` 767–769행 |
| 04-10 | JSON vs JSONB (공백·키 순서 유지 여부, 검색 속도, 인덱스) | ✅ | json은 입력 텍스트를 그대로 보관(공백·키 순서·중복 키 유지), jsonb는 이것들을 버리고 중복 키는 마지막 값만 남긴다. jsonb는 인덱스를 지원한다. 입력은 조금 느리고 처리는 훨씬 빠르다. 대부분 jsonb를 권장한다 | [PostgreSQL Docs: JSON Types](https://www.postgresql.org/docs/current/datatype-json.html), [9.4 버전 문서](https://www.postgresql.org/docs/9.4/datatype-json.html) |
| 04-11 | 메타데이터 필터, `{"$gte": 2025}` 같은 비교 연산자 | ✅ | `$gte` → `>=` 등 비교 연산자를 지원하고, 지원하지 않는 연산자는 오류를 낸다. 설치 버전에서 `use_jsonb` 기본값은 이미 `True`다 | `langchain_postgres/vectorstores.py` 73–97·387·1119행 |

## 검증의 한계

- 코드 동작은 설치된 소스를 읽어서 확인했고, 실제로 실행해 보지는 않았습니다(DB 연결이 필요한 PGVector 포함).
- pgvector 동작은 최신 README 기준입니다. 사용 중인 PostgreSQL에 설치된 pgvector 버전은 확인하지 않았습니다.
- Lost in the Middle 논문은 초록과 공개 요약 기준으로 확인했습니다.
- PostgreSQL의 "입력은 느리고 처리는 빠르다"는 표현은 9.4 버전 문서에 있는 설명입니다. 현재 문서는 "효율이 다르고 jsonb는 인덱스를 지원한다"고만 적고 있습니다.
