## 01. LLM의 한계와 RAG

| # | 노트 내용 | 판정 | 출처 기준 내용 | 출처 |
|:-:|---|:-:|---|---|
| 01-1 | 단어 1개 = 토큰 1개가 아니다 | ✅ | 영어는 대략 4글자 ≈ 1토큰이고, 이것은 추정치일 뿐이다 | [OpenAI Help: What are tokens](https://help.openai.com/en/articles/4936856-what-are-tokens-and-how-to-count-them) |
| 01-2 | 한국어는 조사·어미 때문에 **형태소 단위**로 더 잘게 쪼개진다 (교안) | ⚠️ | 영어가 아닌 언어는 글자 대비 토큰 수가 더 많은 경우가 많다는 점은 **맞다**. 하지만 GPT 계열 토크나이저(tiktoken)는 **BPE** 방식이라, 문법적 형태소가 아니라 학습 데이터에서 자주 나온 글자 조합 단위로 나뉜다. 교안의 `[나][는][AI][를]` 표는 이해를 돕기 위한 예시이고 실제 분할과 다를 수 있다 | [OpenAI Help: tokens](https://help.openai.com/en/articles/4936856-what-are-tokens-and-how-to-count-them), [OpenAI Cookbook: tiktoken](https://developers.openai.com/cookbook/examples/how_to_count_tokens_with_tiktoken) |
| 01-3 | Temperature가 높으면 무작위·창의적, 낮으면 일관·결정적 | ✅ | 범위는 0~2. 0.8 같은 높은 값은 더 무작위, 0.2 같은 낮은 값은 더 집중되고 결정적. `top_p`와 동시에 바꾸지 말라고 권장 | [OpenAI API Reference: Chat Completions](https://developers.openai.com/api/reference/python/resources/chat/subresources/completions/methods/create) |
| 01-4 | Temperature 구간표 (0.0~0.3은 항상 1등만, 0.4~0.7 균형, 0.8~1.0 창의) | ❓ | 공식 문서에는 이런 구간 구분이 없다. 교안의 활용 가이드로 보면 된다. "0~0.3이면 **항상** 1등만"도 공식 문서에 없는 표현이다 | 위와 같음 |
| 01-5 | 컨텍스트 윈도우를 넘으면 가장 오래된 토큰부터 밀려나 잊는다 | ⚠️ | 컨텍스트 윈도우 = 한 요청에서 쓸 수 있는 최대 토큰 수(입력 + 출력 + 추론 토큰 포함)인 건 **맞다**. 하지만 넘쳤을 때 동작은 설정에 따라 다르다. Responses API는 기본값(`truncation: disabled`)이면 **400 오류**, `auto`면 **대화 앞부분부터 삭제**한다. "오래된 것부터 잊는다"는 채팅 앱이 앞부분을 잘라 내는 경우의 설명이다 | [OpenAI Docs: Conversation state](https://developers.openai.com/api/docs/guides/conversation-state), [OpenAI API Reference: Responses](https://developers.openai.com/api/reference/python/resources/responses/methods/create) |
| 01-6 | LLM 한계: 지식 컷오프(학습 시점에 고정) | ✅ | LLM의 두 가지 핵심 한계로 **유한한 컨텍스트**와 **정적인 지식**(학습 데이터가 특정 시점에 고정)을 든다 | [LangChain Docs: Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval) |
| 01-7 | RAG는 검색한 지식을 프롬프트에 넣어 한계를 극복한다 | ✅ | 질의 시점에 외부 지식을 가져와 위 두 한계를 해결하는 것이 RAG의 기반이다 | [LangChain Docs: Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval) |
| 01-8 | RAG는 환각을 줄인다 | ✅ | 검색 증강 모델이 대화에서 환각을 줄인다고 보고 | [Shuster et al. 2021, Findings of EMNLP](https://arxiv.org/abs/2104.07567) |
| 01-9 | LoRA: 기존 파라미터는 그대로 두고 작은 행렬을 **병렬로 통과시켜** 가중치를 더하는 방식으로 서비스, 학습이 빠르다 | ⚠️ | 사전학습 가중치를 고정하고, 각 층에 학습 가능한 저랭크 분해 행렬을 넣는다. 학습 파라미터가 크게 줄고(GPT-3 기준 1만 배) 학습이 빠르다는 건 **맞다**. 단, 서비스할 때는 작은 행렬을 원래 가중치에 **합칠(merge) 수 있어서 추론 지연이 추가되지 않는다**는 것이 논문의 핵심 장점이다. 병렬 구조는 학습할 때의 모습이다 | [Hu et al. 2021, LoRA](https://arxiv.org/abs/2106.09685) |
| 01-10 | PEFT = LLM Base + 추가 파라미터 구조 | ✅ | PEFT는 베이스 모델을 고정한 채 소수의 추가 파라미터만 학습하는 방식이다. LoRA는 PEFT의 대표 방법이다 | [Hugging Face PEFT Quicktour](https://huggingface.co/docs/peft/en/quicktour), [HF smol-course: LoRA and PEFT](https://huggingface.co/learn/smol-course/unit1/3a) |
| 01-11 | 파인튜닝은 기존 파라미터를 유지한 채 새 파라미터를 추가하는 기법 | ⚠️ | 이건 **PEFT 방식**의 설명이다. PEFT 문서는 자신을 "베이스 모델의 **모든 파라미터를 학습하는 것**"과 비교한다. 즉 전체 파인튜닝은 모든 파라미터를 학습(수정)한다. → Claude의 `[보충]`(LoRA 같은 PEFT의 설명이다)은 **✅** | [Hugging Face PEFT Quicktour](https://huggingface.co/docs/peft/en/quicktour) |
| 01-12 | 파인튜닝은 새 정보마다 재학습, 출처 제시 어려움 / RAG는 문서만 바꾸면 된다 | ✅ | RAG 논문은 출처(provenance) 제시와 세계 지식 갱신을 기존 모델의 미해결 문제로 들고, **검색 인덱스를 교체해 모델 지식을 갱신**할 수 있음을 보였다 | [Lewis et al. 2020, RAG](https://arxiv.org/abs/2005.11401) |
| 01-13 | 질문과 맞지 않는 지식을 넣으면 오히려 성능이 나빠진다 | ✅ | 문제에 관련 없는 정보를 섞으면 LLM의 정확도가 크게 떨어진다. 다만 논문은 이를 "환각"이 아니라 **"주의가 흐트러져 정확도가 떨어진다"** 로 표현한다 | [Shi et al. 2023, ICML](https://arxiv.org/abs/2302.00093) |
| 01-14 | RAG 순서: 수집 → 분할 → 임베딩 → (저장) → 검색 → 생성 | ✅ | 문서 로더 → 청크로 분할 → 임베딩 → 벡터 저장소 → (질의 임베딩) → 리트리버 → LLM 답변 | [LangChain Docs: Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval) |

## 02. 임베딩과 유사도

| # | 노트 내용 | 판정 | 출처 기준 내용 | 출처 |
|:-:|---|:-:|---|---|
| 02-1 | 임베딩 모델은 글을 벡터로 바꾸고, 뜻이 비슷하면 가까이 모인다 | ✅ | 임베딩 모델은 텍스트를 숫자 벡터로 바꿔, 뜻이 비슷한 텍스트가 벡터 공간에서 가까이 놓이게 한다 | [LangChain Docs: Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval) |
| 02-2 | `text-embedding-3-small`은 1,536개 숫자 | ✅ | 기본 길이는 1,536 (3-large는 3,072). `dimensions` 파라미터로 줄일 수 있다 | [OpenAI Docs: Embeddings](https://developers.openai.com/api/docs/guides/embeddings) |
| 02-3 | 저장과 검색에 같은 임베딩 모델을 써야 하고, PGVector에 넣은 모델이 둘 다에 자동으로 쓰인다 | ✅ | 설치된 `langchain_postgres` 0.0.19 소스에서 저장(`embed_documents`)과 검색(`embed_query`) 모두 생성자에 넣은 같은 `embeddings` 객체를 호출한다. LangChain 파이프라인 그림도 질의를 같은 방식으로 임베딩해 비교한다 | `chapter03/.venv/.../langchain_postgres/vectorstores.py` 885·942행, [LangChain Docs: Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval) |
| 02-4 | 코사인 유사도: -1 ~ 1, 1이면 같은 방향, 0이면 직각 | ✅ | 범위는 [-1, 1]. 비례하는 벡터는 +1, 직교하면 0, 정반대 방향이면 -1 | [Wikipedia: Cosine similarity](https://en.wikipedia.org/wiki/Cosine_similarity) |
| 02-5 | 코사인 -1에 가까울수록 **반대 의미** | ⚠️ | 수학적으로는 "반대 **방향**"이다. 실제 단어 임베딩에서는 반의어(뜨겁다/차갑다)가 비슷한 문맥에 쓰여서 **오히려 유사도가 중간~높게** 나온다는 연구가 있다. "반대 의미 = -1"로 외우면 안 된다 | [Wikipedia: Cosine similarity](https://en.wikipedia.org/wiki/Cosine_similarity), [IWCS 2023: The Effects of Antonymy and Polysemy](https://aclanthology.org/2023.iwcs-1.17.pdf) |
| 02-6 | 반대 의미도 유의미한 정보라서 실무에서 코사인을 가장 많이 쓴다 | ⚠️ | OpenAI가 코사인 유사도를 **권장하는 것은 맞다**. 하지만 문서는 "거리 함수 선택은 보통 큰 차이가 없다"고 하며, 위 이유는 문서에서 확인되지 않는다. 확인되는 이유는 "벡터 **크기와 무관하게 각도만** 본다"(→ Claude `[보충]`, **✅**)이다 | [OpenAI Docs: Embeddings FAQ](https://developers.openai.com/api/docs/guides/embeddings), [Wikipedia: Cosine similarity](https://en.wikipedia.org/wiki/Cosine_similarity) |
| 02-7 | 내적은 정규화된 벡터면 코사인과 **거의 비슷** | ⚠️ | 길이가 1로 정규화되어 있으면 내적 = 코사인 유사도로 **정확히 같다**. OpenAI 임베딩은 이미 길이 1로 정규화되어 나오므로, 내적으로 계산하면 조금 더 빠르다 | [OpenAI Docs: Embeddings FAQ](https://developers.openai.com/api/docs/guides/embeddings) |
| 02-8 | 유클리드 거리: 작을수록 비슷 | ✅ | 정규화된 OpenAI 임베딩에서는 **코사인 유사도와 유클리드 거리가 같은 순위**를 낸다 (새로 알게 된 점) | [OpenAI Docs: Embeddings FAQ](https://developers.openai.com/api/docs/guides/embeddings) |
| 02-9 | 코사인 거리 = 1 − 코사인 유사도, 범위 0(같은 방향) ~ 2(반대) | ✅ | pgvector의 `<=>`는 코사인 거리이고, 코사인 유사도는 `1 - (embedding <=> ...)`로 구한다 | [pgvector README](https://github.com/pgvector/pgvector/blob/master/README.md) |
| 02-10 | 관련도 점수 = 1 − 코사인 거리 (**0~1**, 클수록 비슷) | ⚠️ | 공식은 **맞다**. 설치된 langchain-core 1.8.1의 `_cosine_relevance_score_fn`은 `1.0 - distance`를 반환하고, PGVector 기본 거리 전략은 COSINE이다. 그런데 1 − 코사인 거리는 결국 **코사인 유사도 그 자체**라서 이론상 범위는 -1~1이다. LangChain은 0~1을 기대하고, 범위를 벗어나면 `"Relevance scores must be between 0 and 1"` **경고만 띄운다**(536·586행) | `chapter03/.venv/.../langchain_core/vectorstores/base.py` 392·536행, `langchain_postgres/vectorstores.py` 63·1859행 |
| 02-11 | 유클리드 거리를 관련도로 바꿀 때 LangChain은 `1 − 거리/√2` | ✅ | `_euclidean_relevance_score_fn`이 `1.0 - distance / math.sqrt(2)`를 반환한다. 코드 주석: **정규화된 임베딩**이면 거리가 0(가장 비슷) ~ √2(가장 다름)라는 가정이다 | `chapter03/.venv/.../langchain_core/vectorstores/base.py` 377–389행 |
| 02-12 | numpy: `np.dot` 내적, `np.linalg.norm` 길이(L2), 배열끼리 뺄셈 | ✅ | `np.linalg.norm`의 기본값은 벡터의 2-노름(L2, 유클리드 길이) | [NumPy: numpy.linalg.norm](https://numpy.org/doc/stable/reference/generated/numpy.linalg.norm.html) |
