## 06. BM25와 하이브리드 검색

|:-:|---|:-:|---|---|
| 06-1 | 의미 검색과 키워드 검색은 잘하는 게 달라서 섞어 쓴다 (하이브리드) | ✅ | Elasticsearch는 BM25(기본 점수 방식)와 벡터 검색 결과를 RRF 등으로 합치는 하이브리드 검색을 공식 지원한다 | [Elastic Docs: Ranking](https://www.elastic.co/docs/solutions/search/ranking), [Elastic Docs: RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion) |
| 06-2 | TF-IDF는 BM25의 전신 | ✅ | BM25와 그 변형은 "TF-IDF와 비슷한(TF-IDF-like) 검색 함수"다 | [Wikipedia: Okapi BM25](https://en.wikipedia.org/wiki/Okapi_BM25) |
| 06-3 | BM = Best Matching, Okapi는 API가 아니라 검색 시스템 이름 | ✅ | BM은 best matching의 약자. Okapi는 처음 이 함수를 쓴 검색 시스템(런던 City University, 1980~90년대) | [Wikipedia: Okapi BM25](https://en.wikipedia.org/wiki/Okapi_BM25) |
| 06-4 | 25 = 25번째 버전, BM25 공식은 1994년쯤 | ❓ | Wikipedia 본문에서 확인되지 않았다 | [Wikipedia: Okapi BM25](https://en.wikipedia.org/wiki/Okapi_BM25) |
| 06-5 | BM25 = TF(포화) + IDF + 문서 길이 보정 | ✅ | 공식의 `k1`이 TF 포화, `b`가 문서 길이 보정을 맡는다. rank_bm25 `BM25Okapi` 기본값은 `k1=1.5, b=0.75` | [Wikipedia: Okapi BM25](https://en.wikipedia.org/wiki/Okapi_BM25), `rank_bm25.py` 78–79행 |
| 06-6 | `BM25Okapi`는 rank_bm25 클래스이고, 내 컴퓨터에서 계산해 API 호출이 없다 | ✅ | `BM25Retriever`가 내부에서 `rank_bm25.BM25Okapi`를 만들어 쓴다. 순수 파이썬·numpy 계산이다 | `langchain_community/retrievers/bm25.py` 55·64행 |
| 06-7 | 기본 토크나이저는 띄어쓰기 분할(`text.split()`) | ✅ | `default_preprocessing_func`가 `text.split()`을 반환한다 | `langchain_community/retrievers/bm25.py` 11–12행 |
| 06-8 | `bm25_retriever.k` 기본 4 | ✅ | `k: int = 4` | `langchain_community/retrievers/bm25.py` 22행 |
| 06-9 | BM25Retriever는 커트라인이 없어서 0점 문서로도 k를 채운다 | ✅ | `get_top_n`이 점수를 내림차순 정렬해서 위에서 n개를 자를 뿐, 점수 기준으로 거르는 코드가 없다 | `rank_bm25.py` 69–75행, `bm25.py` 115행 |
| 06-10 | RRF 점수 = Σ 가중치 × 1/(순위 + 60), 실습 값 0.5/61 등 | ✅ | `weight / (rank + self.c)`, 순위는 1부터(`enumerate(..., start=1)`), `c` 기본값 60, `weights`를 안 주면 균등 분배 | `langchain_classic/retrievers/ensemble.py` 70·87·328–335행 |
| 06-11 | EnsembleRetriever에는 자기 k가 없고, 겹치는 문서를 합쳐 돌려준다 | ✅ | 각 리트리버 결과를 RRF로 합친 뒤 `unique_by_key`로 중복을 제거한다 | `langchain_classic/retrievers/ensemble.py` 36·340행 |
| 06-12 | RRF는 점수 대신 순위만으로 합친다 | ✅ | 여러 검색 시스템의 순위를 합치는 단순한 방법으로, 개별 시스템보다 좋은 결과를 낸다고 보고 | [Cormack et al., SIGIR 2009](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf), [Elastic Docs: RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion) |
| 06-13 | Elasticsearch는 BM25와 벡터를 한 곳에서 하이브리드로 | ✅ | BM25가 기본 점수 방식이고, kNN 검색과 RRF 결합을 지원한다 | [Elastic Docs: Ranking](https://www.elastic.co/docs/solutions/search/ranking) |
| 06-14 | LLM이 질문이 키워드형인지 의미형인지 판단해서 가중치를 정한다 | ❓ | 가능한 설계지만 공식 문서에서 이런 기능·권장을 찾지 못했다. LangChain `EnsembleRetriever`의 가중치는 고정값으로 넣는다 | `langchain_classic/retrievers/ensemble.py` 83–91행 |
| 06-15 | 패키지 위치: BM25Retriever는 community, EnsembleRetriever는 classic | ✅ | 설치된 패키지 경로와 같다 | `langchain_community/retrievers/bm25.py`, `langchain_classic/retrievers/ensemble.py` |

## 07. 리랭킹과 압축

| 07-7 | `ContextualCompressionRetriever` = 기본 검색기 + 후처리기 | ✅ | `base_retriever`로 가져온 뒤 `base_compressor.compress_documents`로 줄인다 | `langchain_classic/retrievers/contextual_compression.py` 16–40행 |

| 07-10 | 리랭킹을 쓰는 이유: Lost in the Middle | ✅ | 관련 정보가 처음·끝에 있을 때 성능이 가장 높다 (05 검증 참고) | [Liu et al. 2023](https://arxiv.org/abs/2307.03172) |

## 검증의 한계

- 코드 동작은 소스를 읽어서 확인했고, 노트북을 다시 실행하지는 않았습니다.
- RRF 논문에서 k=60이 최적값으로 제시됐는지는 본문 실험까지 확인하지 못했습니다. LangChain과 Elasticsearch가 60을 기본으로 쓰는 것만 확인했습니다.
- HyDE는 초록을 직접 열어 확인했습니다. 나머지 논문은 초록·공개 요약 기준입니다.
- ko-reranker의 출력 개수(`num_labels`)는 모델 설정 파일을 직접 열어 보지 않았습니다. 0~1 점수가 나온다는 건 sentence-transformers 기본 동작과 실습 결과로 판단했습니다.
