# 프로젝트 계획서 (초안) — 향수 큐레이션 Knowledge Agent

> 상태: **초안**. 팀 합의 전 항목은 `[결정 필요]`로 표시했다.
> 근거 자료: 발제 문서(AX1 프로젝트3), 튜터님 설명(녹음 정리본), 저장소 학습 노트 `docs/01~10`.
> 가정: 주제는 "가상 향수 카탈로그 기반 상담 지원 Agent"로 잡았다. 다른 주제로 바뀌면 3·4·5장만 교체하면 된다.

## 1. 한 줄 요약

> 고객은 "비 오는 날 숲 냄새, 너무 무겁지 않은 거"라고 묻는데, 카탈로그에는 "베티버, 우디, 라이트 지속력"이라고 적혀 있다.
> **고객의 말과 문서의 말이 다른 문제**를, BM25+Vector 하이브리드 검색·재정렬·쿼리 리라이트로 풀고, 그 효과를 원본 기록으로 증명한다.

## 2. 왜 이 주제인가 (스토리)

1. **현장의 문제**
   - 향수 매장 직원과 온라인 CS 담당자는 수십~수백 개 제품의 노트 구성, 농도(EDT/EDP), 계절, 지속력, 교환 정책을 다 외울 수 없다.
   - 고객은 용어가 아니라 **분위기와 상황**으로 묻는다. 키워드 검색은 못 찾고, 벡터 검색은 비슷한 향을 가져오되 "EDT인지 EDP인지", "리뉴얼로 바뀐 제품인지" 같은 **정확한 조건**을 틀린다.
   - 잘못된 안내는 교환·환불·클레임으로 이어진다. 그래서 답변은 반드시 **근거 위치와 함께** 나가야 한다.
2. **RAG를 쓰는 이유가 문제 안에 있다**
   - BM25는 제품명·농도·용어에 강하고, Vector는 감성 표현에 강하다. 재정렬은 비슷한 두 제품 중 질문에 맞는 쪽을 가려낸다. 세 구성의 차이가 **문제의 성격에서 자연스럽게** 나온다.
3. **왜 가상 카탈로그인가**
   - 실제 향수 사이트는 스크래핑 금지 약관과 저작권이 걸린다.
   - 모델이 실제 제품을 기억으로 답하면 "문서 근거"인지 구분할 수 없다. 가상 데이터는 모델의 사전 지식이 0이라 **근거 인용 평가가 깨끗**하다.
4. **하지 않는 주장**
   - 개선 전 상담 시간을 측정하지 않았으므로 "시간 절감률"을 성과로 말하지 않는다.
   - 작은 평가셋과 가상 문서 범위의 검증임을 보고서에 명시한다.

## 3. 문제 정의 (`docs/problem.md` 뼈대)

| 항목 | 내용 |
|---|---|
| 사용자 | 향수 매장 직원, 온라인 CS 담당자 (신규 입사자 포함) |
| 기존 탐색 과정 | 카탈로그 PDF/엑셀 검색, 동료에게 질문, 감에 의존 |
| 질문 범위 | 제품 노트·농도·계절·지속력, 유사 제품 구분, 용어 의미, 샘플·교환·환불 정책, 레이어링 가이드 |
| 오답·근거 부족의 영향 | 잘못된 제품 추천, 농도 착오로 인한 교환·클레임, 카탈로그에 없는 내용을 지어내 안내 |
| RAG 선택 이유 | 문서가 많고 갱신되며 출처 확인이 필요함. 모델 단독 답변은 근거를 보장하지 못함 |
| 제외 범위 | 실제 판매·결제·발송, 모델 학습·파인튜닝, 알레르기·피부 반응 등 **의학적 판단**(문서에 적힌 표기만 안내) |

## 4. 성공 기준 (결과를 보기 전에 확정) `[결정 필요: Day 1]`

우선순위 제안: **① 품질(근거 적합·근거 없음 대응) > ② 지연 > ③ 비용**

| 지표 | 정의 | 목표값 `[팀 합의로 확정]` |
|---|---|---|
| Hit@5 | 허용 근거 청크가 상위 5개 안에 하나 이상 (분모 17) | 예: B ≥ A, C ≥ B |
| 정답 충족 | 필수 핵심 사실이 모두 맞고 모순 없음 (분모 17) | 예: 0.7 이상 |
| 근거 적합 | 인용이 실제 검색 결과에 있고 주요 주장을 뒷받침 (분모 17) | 예: 0.8 이상 |
| 근거 없음 대응 | 무근거 단정 없이 정보 부족 안내 (분모 3) | 예: 3/3 |
| 호출 성공률·오류·timeout | 시도 대비 성공 수 | 기록 |
| 응답 시간 | 성공 호출의 평균·중앙값·n (검색+생성+리라이트 포함) | 기록 |
| **추가 지표 (튜터님 권고)** | 토큰 사용량, TTFT(첫 토큰까지 시간) | 기록 |

**Trade-off 판단 규칙도 사전에 적는다.** 튜터님 예시: "품질이 0.1 오르는데 비용이 3배면 도입할지 따진다."
→ 예: "Hit@5가 0.1 미만으로 오르고 토큰 비용이 2배 이상이면 도입하지 않는다" 같은 문장을 Day 1에 확정해 둔다.

## 5. 데이터 설계

### 5.1 문서 구성 (가상, 실제 브랜드명 사용 금지)

| 문서 유형 | 수량 | 내용 |
|---|---|---|
| 제품 카드 | 약 40 | 제품명, 농도(EDT/EDP), 탑·미들·베이스 노트, 향 계열, 계절, 지속력, 가격대, 유사 제품과의 차이 |
| 용어집 | 1 | 우디·머스크·시트러스 등 용어 정의 |
| 응대 FAQ·정책 | 3~4 | 샘플, 교환·환불, 레이어링, 보관 |
| 정오표(리뉴얼 공지) | 1~2 | 일부 제품 카드를 덮어쓰는 변경 사항 → 문서 버전 혼동 설계 |

### 5.2 혼동 설계 (평가 요건: 유사 용어·예외 최소 2개 문서)
- 같은 이름, 다른 농도(EDT vs EDP)
- 노트가 거의 같은 두 제품, 한 가지가 다른 경우
- 정오표가 제품 카드의 지속력·노트를 바꾼 경우
- 용어집의 정의와 제품 카드 표현이 다른 경우

### 5.3 메타데이터·청크
- 문서 목록: 문서 ID, 제목, 출처(작성 방식), 이용 조건, 버전, 수집(작성) 시점, 원문 위치
- 청크 필드: 청크 ID(예: `PRD-012#notes`), 문서 ID, 위치(절·행), 제품명, 농도, 계절, 가격대, 유형(제품/용어/정책/정오표)
- 청크 크기·겹침·임베딩 모델·색인 버전을 실행마다 기록

### 5.4 작성·검수 원칙
- LLM으로 초안을 만들되 **생성 모델과 프롬프트를 문서 목록에 기록**한다 (튜터님: 프롬프트도 기록).
- 정답은 **카탈로그 원문에서 사람이 직접 확인**한다. LLM이 쓴 문서와 정답을 그대로 믿지 않는다.
- 평가용 정답표는 검색 문서나 프롬프트에 섞지 않는다.

### 5.5 한국어 BM25 `[확인 필요]`
문서가 한국어라 조사 처리 없이는 BM25가 약해진다. 형태소 분석기 또는 n-gram 토크나이저 중 설치·실행 가능한 것을 개발셋에서 비교해 선택하고 기록한다.

## 6. 평가셋 설계 (총 30문항)

| 구분 | 구성 |
|---|---|
| 개발용 10 (`eval/dev.json`) | 답변 가능 8, 근거 없음 2 |
| 최종용 20 (`eval/test.json`) | 직접 검색 10, 표현 변형·유사 조건 구분 7, 근거 없음 3 |

튜터님의 3유형(단일 문서, 복합 추론, 문서 외)은 위 틀 안에 이렇게 배치한다.
- 단일 문서 → 직접 검색
- 복합 추론 → 표현 변형·유사 조건 구분 안에 **다중 근거 문항**(제품 카드 + 용어집)을 포함 (다중 근거 누락은 별도 분석)
- 문서 외 → 근거 없음

**문항 예시 (가상 제품명 `아르부스` 사용)**

| 유형 | 예시 질문 | 기대 |
|---|---|---|
| 직접 검색 | "아르부스 EDP의 베이스 노트는?" | 카드의 베이스 노트 |
| 표현 변형 | "비 오는 날 숲 냄새 나고 무겁지 않은 향수 있어?" | 해당 계열·지속력 제품 |
| 유사 조건 구분 | "아르부스 EDT와 EDP는 지속력이 어떻게 달라?" | 두 카드의 차이 |
| 정오표 | "리뉴얼 후 아르부스의 탑 노트가 바뀌었어?" | 정오표 기준 |
| 다중 근거 | "베티버가 들어간 제품 중 겨울용은?" | 용어집 + 제품 카드 |
| 근거 없음 | "아르부스를 알레르기 있는 사람이 써도 안전해?" | 정보 부족 안내 |
| 근거 없음 | "다음 달 신제품 출시일은?" | 정보 부족 안내 |

**검토 절차**: 1차 작성 → 팀 교차 확인 → LLM 적합성 검토(튜터님 권고) → **LLM 검토와 사람 검토를 분리 기록** → 버전 고정. 최종 20문항은 실행 전 태그로 동결하고 튜닝에 쓰지 않는다.

## 7. 시스템 구성

```
질문 → (리라이트: 선택) → BM25 + Vector → RRF 결합 → reranker → 근거 선택 → 답변·출처 / 근거 부족 안내
```

| 구성 | 내용 |
|---|---|
| A | Vector만 (임베딩 모델, 검색 개수 기록) |
| B | BM25 + Vector, RRF 결합 (후보 수·가중치·중복 제거 규칙 기록) |
| C | B 후보를 reranker로 재정렬 (reranker, 입력 후보 수, 출력 k 기록) |
| 최적화 | **쿼리 리라이트 추천** `[결정 필요]` |
| 인터페이스 | Streamlit (질문·답변·근거·오류 표시) |

**리라이트를 추천하는 이유**: "분위기 표현 → 카탈로그 용어(향 계열·노트)로 변환"이 이 문제의 핵심 간극이라, 스토리와 최적화가 일치한다. 필수 검증은 C 대비 C+리라이트 20건, 원질문·변환 질의 저장, 정답·근거를 리라이터에 주지 않기, 오류 시 원질문 fallback이다.
캐싱을 고르면 15건(5문항 × 미적중·적중·버전 변경 후)이며 키·TTL·무효화 정책 설계가 중심이 된다.

공통 규칙: A/B/C는 같은 생성 모델·프롬프트·출력 한도를 쓴다. 근거 부족 판정 방법은 개발셋으로 정한다. 검색 실패·모델 오류와 정상적인 "근거 없음"을 구분한다. 문서 속 지시문은 데이터로만 취급한다.
모델(임베딩·생성·reranker) 선정은 `[확인 필요: 실행 가능성과 사용 조건]`.

## 8. 실험 계획과 기록 (튜터님 권고 반영)

- **기본 60건**: A/B/C × 최종 20문항 × 1회. **분기 20건**: C+리라이트.
- 워밍업·실패·재시도·추가 실험은 별도 식별자로 구분하고, 실패 삭제와 좋은 결과만 고르는 재실행은 하지 않는다.
- 최종 결과를 본 뒤 튜닝한 실험은 본 평가와 분리한다.
- 실행 기록(JSON/CSV): 실행 ID, 질문 ID, 구성, 문서·색인·모델·프롬프트 버전, 검색 후보·점수, 재정렬 전후 순위, 원본 답변, 출처, 시간, 상태, 채점 근거.
- **프롬프트·실험 정리 엑셀** (튜터님: 추후 활용용)

| 시트 | 내용 |
|---|---|
| prompt_versions | 프롬프트 ID, 용도, 전문, 모델, 변경 이유, 사용한 실행 ID |
| runs | 실행 ID, 구성, 설정, 일시, 상태 |
| eval_summary | 구성별 지표(Hit@5, 정답, 근거, 근거 없음, 성공률, 시간, 토큰, TTFT) |
| failures | 실패 유형(검색 누락·순위 실패·생성 오류·잘못된 인용·근거 없음 대응 실패), 대표 사례 |
| lessons | 배운 점·노하우 (최종 프로젝트 재활용) |

## 9. 5인 역할 분담

과제문의 역할 9개를 5명에게 배치했다. 겸임은 가능하되 **모든 팀원이 코드 작성, 실행 검증, 타인 리뷰에 참여**한다.

| 담당 | 주 역할 | 주요 산출물 | 교차 리뷰 대상 |
|---|---|---|---|
| **P1 문제·평가 설계** | 문제 정의, 성공 기준, 평가셋 30문항 관리, 개발/평가 분리 감시, 채점 루브릭 | `problem.md`, `eval/*.json`, 루브릭 | P5의 채점 결과 검토 |
| **P2 문서·색인** | 가상 카탈로그 작성·검수, 청킹, 메타데이터, 색인 재생성 스크립트, 문서 목록 | `data/`, 전처리 코드, 문서 목록 | P1의 평가셋 정답·근거 매핑 검증 |
| **P3 검색·재정렬** | A/B/C 검색, RRF, reranker, 전후 순위 기록 | 검색 모듈, 설정 | P2의 청크·색인 PR 리뷰 |
| **P4 응답·최적화** | 프롬프트, 근거 인용, 근거 없음 처리, 리라이트(또는 캐싱), Streamlit | 응답 체인, UI, 프롬프트 기록 | P3의 검색 PR 리뷰 |
| **P5 실험·분석·통합** | 실행기, 로그 스키마, 60+20건 실행, 비교표, 실패 분석, README, 제출 태그, 프롬프트 엑셀 | `results/`, `report.md`, README | P4의 응답 PR 리뷰 |

- 채점은 **작성자와 다른 사람이** 맡는다 (예: P1 문항을 P5가, P2 문서 관련 문항을 P1이).
- 재현 확인: P2가 P5의 README만 보고 색인 재생성과 대표 사례 재실행 (`contributions.md`에 기록).
- 개인별 근거(PR, 실행 기록, 리뷰 코멘트)를 `contributions.md`에 남긴다.

## 11. 협업·보안 규칙
- 브랜치 + PR 리뷰. 최종 평가셋·색인·설정은 태그로 고정(예: `eval-v1-frozen`).
- `.env`, API 키, 가상환경, 대용량 색인은 올리지 않고 위치·버전·재생성 방법만 기록.
- 사용자별 캐시를 쓰는 경우 사용자 범위를 키에 포함.
- 공개 배포·보안 인증을 달성했다고 주장하지 않음.

| 하이브리드·reranker가 개선되지 않음 | 결과 그대로 보고하고 원인을 분석 (발제 문서도 허용) |
